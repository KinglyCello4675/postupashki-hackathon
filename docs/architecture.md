# Архитектура системы измерения маркетинга

## Главная идея

Превратить путь пользователя от рекламы до покупки в измеримую систему.

Реклама → placement_id → пользователь → покупка → выручка → атрибуция → ROMI → решение по бюджету


## Три уровня знания

### Что мы знаем (реальные данные)

- Продажи: 795 строк, 606 покупателей, 18 курсов, 04.08–10.09.2026.
- Три всплеска продаж: 8–10 августа, 22–24 августа, 4–6 сентября.
- Рекламная активность: размещения и репосты в Telegram-каналах (даты, подписчики, просмотры).
- Динамика подписчиков канала.
- Пики подписчиков не совпадают с пиками продаж (корреляция ≈ 0).

### Что мы оцениваем (модели и предположения)

- Атрибуция: last touch + linear.
- Attributed Revenue по размещениям.
- ROMI по каналам (на demo-данных).
- Прогноз продаж (baseline + backtest).

### Что пока узнать нельзя

- Точный исторический ROMI конкретных размещений.
- Реальный причинный эффект рекламы (incrementality).
- Стоимость конкретных размещений (cost).
- Точную связь «пользователь ↔ рекламное касание» за прошлый период.

## Сущности

| Сущность | Что описывает | Ключевые поля |
|---|---|---|
| Campaign | Рекламная кампания | campaign_id, name, start_date |
| Placement | Конкретное размещение | placement_id, channel, publication_time, cost, creative_id |
| Creative | Креатив | creative_id, type, text |
| Channel | Канал размещения | channel_id, name, subscribers |
| User | Пользователь | user_id, first_touch_time |
| Touch | Касание | touch_id, user_id, placement_id, touch_time |
| Lead | Лид (обратился к менеджеру) | lead_id, user_id, lead_time |
| Payment | Оплата | payment_id, user_id, amount, payment_time |
| Order | Заказ | order_id, user_id, amount, courses |
| Course | Курс | course_id, name, price |

## Как связываем (user stitching)

Рекламный пост с tracking-ссылкой
↓
Пользователь кликает → получает source (placement_id)
↓
Пишет менеджеру → lead с source
↓
Оплачивает → payment с source
↓
Считаем revenue по placement_id


Если source неизвестен — помечаем `unknown`, покупку не выбрасываем.

## Атрибуция

Для MVP используем две модели:

- **Last touch** — вся выручка идёт последнему касанию.
- **Linear** — выручка делится поровну между всеми касаниями.

Окно атрибуции: 14 дней до покупки (обоснование — в `docs/spec.md`).

## ROMI

ROMI = (Attributed Revenue − Cost) / Cost


- Если cost неизвестен — ROMI не считаем.
- Считаем ROMI_attr (на основе атрибуции).
- ROMI_inc (на основе incrementality) не считаем — нет данных.

## Что даёт бизнесу

1. Понимание, какие размещения приносят деньги (после запуска системы).
2. Список каналов с положительным и отрицательным ROMI.
3. Рекомендацию по распределению следующего бюджета.

## Ограничения

- Исторический ROMI по размещениям восстановить нельзя.
- Атрибуция ≠ incrementality.
- Синтетические данные явно помечены.

# Спецификация атрибуции и метрик

## Главная цель системы

Бизнес исторически почти не логировал маркетинговые касания и источники пользователя.
Мы строим систему, которая:

1. Фиксирует каждый этап воронки **до оплаты** (оплата уже логируется).
2. Связывает покупку с источником, который её привёл.
3. Считает ROMI по каждому placement и channel.
4. Показывает, какая реклама окупается, и рекомендует, куда направить бюджет.

**Воронка:**  
реклама → переход/просмотр → основной канал → менеджер → оплата → курс  

Логируется всё, кроме оплаты (она уже есть в base.xlsx). Задача — восстановить путь **от покупки назад к рекламе**.

## 1. Сущности и связи

**Для каждого события фиксируем:**  
`кто → что сделал → когда → откуда пришёл → к какой рекламной активности относится`

| Сущность  | Ключевые поля                                               | Источник                  |
| :---      | :---                                                        | :---                      |
| Channel   | channel_id, name, subscribers                               | реестр каналов            |
| Campaign  | campaign_id, name, start_date                               | реестр размещений         |
| Placement | placement_id, channel, publication_time, cost, creative_id  | реестр размещений         |
| Creative  | creative_id, type, text                                     | реестр размещений         |
| User      | user_id, first_touch_time                                   | base.xlsx + бот           |
| Touch     | touch_id, user_id, placement_id, touch_time                 | бот / менеджер            |
| Lead      | lead_id, user_id, lead_time                                 | менеджер / бот            |
| Payment   | payment_id, user_id, amount, payment_time                   | base.xlsx                 |
| Order     | order_id, user_id, amount, courses                          | агрегация payment         |
| Course    | course_id, name, price                                      | справочник                |


**Описание сущностей:**  
1. **Channel** — канал в Telegram или VK, где размещается реклама. Свой канал — «Поступашки», внешний — канал блогера. `type` нужен, чтобы отделять собственный канал (cost = 0) от платных размещений.
2. **Campaign** — маркетинговая кампания: один запуск, одна акция или серия размещений с общей целью. Объединяет несколько placements, чтобы считать ROMI на уровне кампании, а не только отдельного поста.
3. **Placement** — конкретное размещение рекламы: пост у блогера, нативный пост в своём канале, сторис. Содержит `publication_time` и `cost` — без них ROMI не считается. Одно размещение = одна строка в реестре.
4. **Creative** — креатив внутри размещения: текст, картинка, тип. Нужен, чтобы различать варианты поста и понимать, какой из них сработал.
5. **User** — обезличенный покупатель. `user_id` — хеш Telegram username, как в base.xlsx. Одинаковый хеш во всех таблицах → можем связать касание, лида и оплату без персональных данных.
6. **Touch** — касание пользователя с рекламой. Фиксируется ботом по deep link или менеджером. Один пользователь может иметь несколько касаний — все сохраняются с `touch_time`, чтобы работало окно атрибуции.
7. **Lead** — старт диалога с менеджером и интерес к продукту. Ключевая точка между рекламой и оплатой: именно тут фиксируется `source` (откуда пришёл) и `product_interest` (что хочет купить).
8. **Payment** — факт оплаты. Уже логируется в base.xlsx. Поля: `user_id`, `amount`, `payment_time`.
9. **Order** — заказ, объединяющий одну или несколько оплат. Нужен для пакетных покупок (например, 9 990 ₽ за два курса): в payment будет несколько строк, в order — одна. `is_bundle` помечает такие заказы.
10. **Course** — справочник курсов: название, цена, категория. Нужен, чтобы считать revenue по продуктам и отделять ПРО от базы.

**Источники:**
1. **Реестр каналов** — справочник всех каналов, где размещается реклама: свои и внешние. Заполняется вручную один раз, обновляется при появлении нового канала.
2. **Реестр размещений** — таблица placements.csv, заполняется вручную при закупке рекламы. Поля: channel, campaign, creative, publication_time, cost. Это основной источник данных для ROMI: без cost и publication_time ROMI не считается.
3. **base.xlsx** — реальный обезличенный слой продаж от организаторов: 795 строк, 606 покупателей, 18 продуктов, 04.08–10.09.2026. Поля: student_id, amount, course, timestamp. Это единственный источник реальных payment.

**Бот / менеджер** — два канала фиксации touch и lead:  
1. бот — по deep link `t.me/<bot>?start=<placement_id>`;
2. менеджер — вручную фиксирует source, если deep link не сработал.

**Связи:**  
- **Channel 1→N Campaign 1→N Placement**  
  Channel 1→N Campaign — один канал может быть площадкой для нескольких кампаний.  
  Campaign 1→N Placement — одна кампания включает несколько размещений.  
- **Placement 1→N Touch N→1 User**  
  Placement 1→N Touch — одно размещение даёт много касаний.  
  Touch N→1 User — каждое касание принадлежит одному пользователю.  
- **User 1→N Lead 1→N Payment N→1 Order**  
  User 1→N Lead — пользователь может начать несколько диалогов с менеджером.  
  Lead 1→N Payment — из одного диалога может выйти несколько оплат.  
  Payment N→1 Order — оплата принадлежит одному заказу.  
- **Order N→N Course**  
  Order N→N Course — в заказе может быть несколько курсов, курс может быть в разных заказах.

## 2. Логирование воронки

### Этап 1. Реклама → переход/просмотр

**Что логируем:** публикацию поста/размещения.  

**Как:**
- `collect_posts.py` собирает посты из своих каналов через `t.me/s/<channel>`.
- Для внешних размещений — реестр `placements.csv` заполняется вручную при закупке.
- Каждому placement присваивается `placement_id`, каждому creative — `creative_id`.

**Поля:** `channel, placement_id, creative_id, publication_time, cost`  

### Этап 2. Переход/просмотр → основной канал

**Что логируем:** факт, что пользователь пришёл из рекламы.  

**Как — два механизма:**  

1. **Deep link в бота менеджера** (основной)
   - Ссылка вида `t.me/<manager_bot>?start=<placement_id>`
   - Бот при `/start` сохраняет `start_param` и `user_id` в `touches`.

2. **Переход на сайт / VK**
   - Ссылка с UTM: `?utm_source=placement&utm_campaign=<placement_id>`
   - На сайте — форма «откуда вы о нас узнали» + кнопка в бота менеджера с тем же `start_param`.

**Поля:** `touch_id, user_id, placement_id, source, touch_time`  

### Этап 3. Основной канал → менеджер

**Что логируем:** начало диалога и интерес к продукту.

**Как:**
- Бот менеджера при первом сообщении пишет `conversation_started` с `user_id`, `source` (из deep link или от менеджера), `product_interest`.
- Менеджер при ручном старте диалога заполняет поле `source` в CRM/таблице (простейший вариант — Google Sheet или команда в боте).

**Поля:** `lead_id, user_id, product_interest, source, conversation_started_at, manager_id`

### Этап 4. Менеджер → оплата

**Что логируем:** уже логируется в `base.xlsx` (payment).  

**Как:** при оплате менеджер фиксирует `user_id`.   
`user_id` = хеш Telegram username — как в исходных данных.  

**Поля:** `payment_id, order_id, user_id, amount, course, timestamp`  

### Этап 5. Оплата → курс  

Уже есть в `base.xlsx`. Доступ выдаётся после оплаты.

## 3. User stitching

**Цель:** связать рекламный контакт → Telegram-пользователя → lead → оплату.  

**Основной механизм (deterministic):**  
`Канал А → tracking link (t.me/bot?start=<placement_id>) → Telegram user (start_param + user_id) → менеджер (source из start_param или от менеджера) → payment (user_id совпадает)`  

**Ключевой идентификатор:** `user_id` = хеш Telegram username. Используется во всех таблицах. Персональные данные не храним.  

**Если пользователь читал канал несколько дней и имел несколько касаний:**  
- Все touch сохраняются с `touch_time`.  
- При оплате берём все касания в окне 14 дней.  

**Если deterministic stitching невозможен:**  
- Fallback 1: **self-reported source** — менеджер спрашивает «Откуда вы о нас узнали?» и фиксирует.
- Fallback 2: **probabilistic matching** — сопоставление по времени (касание ≤ 14 дней до оплаты) + канал, если других данных нет.
- Fallback 3: если ничего не сработало → `organic`.

**Ограничения Telegram:**
- Нет админ-доступа к чужим каналам → внешние размещения только через реестр.
- Нет внутренних переписок → бот логирует только факт старта диалога и source.

## 4. Tracking внешней рекламы

**Схема:**
`channel → placement → creative → user/touch → lead → purchase → revenue`

**Идентификаторы:**
- `channel_id` — уникальный ID канала.
- `campaign_id` — ID кампании (например, «запуск ПРО сентябрь»).
- `placement_id` — ID конкретного размещения (канал + дата + креатив).
- `creative_id` — ID креатива внутри placement.

**Передача пользователю:**
- Deep link: `t.me/<bot>?start=<placement_id>`
- UTM на сайт: `?utm_source=placement&utm_campaign=<placement_id>`

**Обязательные поля в таблице placements:**  
`placement_id, channel, campaign, creative_id, publication_time, cost`  

Без `publication_time` и `cost` ROMI не считается.

## 5. Атрибуция

### Модель
- **Last touch** (основная) — вся выручка идёт последнему касанию в окне.
- **Linear** (сравнение) — выручка делится поровну между всеми касаниями в окне.

### Окно атрибуции
- 14 дней до покупки.
- Обоснование: при анализе была получена такая тенденция, что три всплеска по ~3 дня, между ними 10–14 дней затишья. Окно покрывает цикл «пост → прогрев → покупка» и не размывает атрибуцию между запусками.

### Правила распределения revenue
- Касаний нет → `organic`.
- Одно касание → 100% ему.
- Несколько касаний → по правилу модели (last touch / linear).
- Повторные покупки → атрибутируем отдельно, флаг `is_repeat`.
- Пакетные покупки (несколько курсов в одном заказе) → revenue делится пропорционально цене курсов; общий `order_id`.
- `cost` есть только у внешних placement → ROMI считаем только для них.
- Органика (собственный канал, акции) → cost = 0, ROMI не считаем.

### Инверсный путь
`payment → user_hash → lead → touch → placement → channel → campaign`

Идём от покупки назад: находим user_hash в payment, ищем его lead, затем touch в окне 14 дней, затем placement и channel. Так восстанавливаем, какая реклама привела к покупке.

### Attribution ≠ Incrementality

**Разделение:**
- **Attribution** — кому модель приписала уже случившуюся продажу.
- **Incrementality** — появилась ли продажа благодаря рекламе вообще.

Рост продаж после поста не доказывает, что это именно пост дал рост.

**Что предложить для проверки:**
A/B-тест, holdout, randomized promotion, audience split, DiD, synthetic control, interrupted time series.

**Дополнительный пункт:**
В данных есть третий пик (04–06.09), который **не связан с просмотрами постов** — медианные ~20к просмотров и обычная цена. Возможная причина — запуск разборов стажировки в Т-Банк в линейке ПРО.

Это кейс, когда корреляция «пост → продажи» отсутствует, а бизнес-событие (бонус в продукте) работает. Вывод для бизнеса: можно увеличивать число покупателей не только рекламой, но и дешёвыми нематериальными бонусами (разборы, стажировки, гостевые лекции). Это **гипотеза**, её нужно проверять отдельным экспериментом.

## 6. ROMI

Формула: ROMI = (Attributed Revenue − Cost) / Cost  

- `ROMI_attr` — по модели атрибуции (last touch / linear).
- `ROMI_inc` — по incrementality (не считаем, нет данных).
- `cost` неизвестен → ROMI не считаем (органика, акции, собственный канал).
- Считаем на уровне `placement_id`, агрегируем до `channel_id`.

**Минимальный набор данных для подсчёта ROMI:**
1. Placement (placement_id, channel, publication_time, cost, creative_id, promo_code)
2. Touch (touch_id, user_hash, placement_id, touch_time)
3. Payment (payment_id, order_id, user_hash, amount, course, promo_code, timestamp)

---

## 7. Ограничения

- Исторический ROMI восстановить нельзя: нет cost и касаний.
- Нет cost → нет ROMI.
- Нет касаний → атрибуция только на demo-данных (`mock_touches.csv`).
- Incrementality не проверяется: нет экспериментальных данных.
- Третий пик (04–06.09) не объясняется просмотрами постов — это гипотеза.
- Внешние каналы: нет админ-доступа, только публичные данные.
